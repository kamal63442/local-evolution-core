# Evaluation Methodology

The purpose of evaluation in Local Evolution Core (LEC) is to determine whether a candidate local improvement produces a real, generalizable benefit rather than merely improving performance on familiar examples or exploiting weaknesses in the evaluator.

## Core comparison

The simplest study compares:

1. **Baseline agent** — no persistent candidate-generated improvement.
2. **Persistent agent** — may retain local improvements.
3. **Controlled persistent agent** — may retain improvements only after evaluation and human promotion.

## Evaluation roles

A trial may separate the following roles:

- **Proposer** — creates a candidate artifact.
- **Independent evaluator** — assesses candidate quality on unseen tasks.
- **Adversarial critic** — searches for overfitting, evaluator exploitation, unsafe transfer, and hidden regressions.
- **Objective harness** — measures task success and resource use.
- **Human reviewer** — decides whether evidence is sufficient for promotion.

## Why cross-model evaluation matters

If the same model family proposes and judges an improvement, correlated reasoning patterns may inflate confidence in a weak candidate.

LEC therefore treats evaluator diversity as an experimental variable. Candidate artifacts can be generated by one model family and judged by another. Disagreement should be recorded explicitly rather than averaged away without analysis.

## Held-out and sealed tasks

Evaluation should include tasks unavailable to the proposer during candidate generation.

Useful categories include:

- held-out tasks from the same distribution
- sealed regression tests
- adversarial variants
- changed wording with equivalent objectives
- transfer to a new tool configuration
- cross-model transfer
- out-of-distribution tasks

A candidate that only improves training-visible tasks should not be treated as general improvement.

## Replication

Single-run wins are weak evidence. Where budget allows, each condition should be repeated across multiple seeds, task orders, or independent sessions.

Replication helps distinguish persistent gains from stochastic variation.

## Ablation testing

Ablations should remove one component at a time to estimate its contribution.

Examples:

- remove cross-model evaluation
- remove quarantine
- remove rollback
- remove provenance
- remove human promotion
- remove held-out tests
- remove resource ceilings

## Planned metrics

| Metric | Interpretation |
|---|---|
| Task success rate | Whether the system solves more tasks correctly |
| Regression rate | Whether new artifacts harm previously solved tasks |
| Token usage | Whether improvement increases or reduces inference cost |
| Tool-call count | Whether workflows become operationally more efficient |
| Evaluator disagreement | Whether model families assess the same candidate differently |
| Transfer performance | Whether gains survive across tasks/models/environments |
| Failed-promotion rate | How many candidates are rejected by gates |
| Rollback frequency | How often promoted changes later prove harmful |
| OOD performance | Whether gains survive distribution shift |

These are planned measures, not reported results.

## Promotion criteria

A candidate should only be considered for promotion when it satisfies predefined criteria such as:

- no critical integrity violation
- no disallowed scope expansion
- measurable benefit on held-out evaluation
- no unacceptable regression
- acceptable resource cost
- provenance record complete
- human review completed

Promotion thresholds should be chosen before looking at candidate outcomes whenever practical.

## Evaluator exploitation tests

The evaluation process should look specifically for candidates that:

- manipulate scoring language instead of task behavior
- alter evaluation files or reference data
- exploit formatting or parser weaknesses
- improve proxy metrics while degrading real outcomes
- overfit to known examples
- produce persuasive explanations unsupported by objective tests

## Reporting

Future result reports should include:

- model and version identifiers where available
- task-suite description
- baseline definition
- candidate-generation procedure
- evaluation procedure
- sample size / repeat count
- failures and exclusions
- confidence or uncertainty information where meaningful
- limitations

No benchmark claim should appear in this repository without enough methodological context to understand what was actually tested.
